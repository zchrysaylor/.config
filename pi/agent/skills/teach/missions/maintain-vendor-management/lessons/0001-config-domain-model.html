The Vendor Configuration Model

One data class, six optional sections, three scopes, four owners. Master this and half of VMS stops being mysterious.
Why this first? Vendor configuration is the beating heart of VMS — it's what operators edit, what DWH syncs, what gets published to Order Processing, and what lives in that configurations JSONB column. Nearly every incident and PR you'll touch passes through this model. Get the shape in your head and you can read the rest of the service. This is your first tangible win: look at any config field and know what section it lives in, who's allowed to write it, and whether changing it is safe.

A vendor's entire configuration is a single Kotlin data class called PlatformVendorConfig. It is not stored as columns — it's serialized to JSON and dropped into one JSONB column. That one fact drives most of the rules you'll learn later.

1The aggregate: PlatformVendorConfig

Here is the actual class — the whole thing. Read it, then read the annotations.

vendor-management-service/…/db/model/PlatformVendorConfig.kt@JsonIgnoreProperties(ignoreUnknown = true)
@JsonInclude(JsonInclude.Include.NON_EMPTY)
data class PlatformVendorConfig(
    val orderProcessing: OrderProcessingConfiguration? = null,
    val vendorAvailability: VendorAvailabilityConfiguration? = null,
    val vendorMonitor: VendorMonitorConfiguration? = null,
    val avoidableWaitingTime: AvoidableWaitingTimeConfiguration? = null,
    val preparationTime: PreparationTimeConfiguration? = null,
    val orderCancellationFees: OrderCancellationFeesConfiguration? = null,
    val vendorAttributes: Map<String, Any?>? = null
) {
    companion object {
        fun empty() = PlatformVendorConfig(
            orderProcessing = OrderProcessingConfiguration(),
            /* …all six sections, non-null and empty… */
        )
    }
}
Kotlin ↔ Java
  • data class ≈ a Java record, but mutable-by-copy: you get equals/hashCode/toString and a generated .copy(...) (like Lombok @With). You'll use .copy() constantly — see §2.
  • val = final field. Every field here is immutable. To "change" a config you build a new one with .copy().
  • The ? after a type (OrderProcessingConfiguration?) means nullable. Without it, the compiler forbids null. This is enforced — the build uses -Xjsr305=strict.
  • = null is a default argument. Callers can omit any field. There's no builder and no telescoping constructors — named args + defaults replace both.
  • companion object ≈ the static members of the class. PlatformVendorConfig.empty() is a static factory.

The mental model

Think of a config as a bag of six optional feature-sections plus one dynamic map:

PlatformVendorConfig
orderProcessing — accept timings, stacking, vehicle restrictions
avoidableWaitingTime — AWT fees/exclusions
preparationTime — prep intervals
orderCancellationFees — cancellation fees
vendorAvailability — check-in/out (mixed owner)
vendorMonitor — grades & monitor rules (mixed owner)
vendorAttributes — arbitrary DWH fields (dynamic map)

operator-ownedDWH-fed / mixed — full ownership breakdown in §4

Any section can be null ("this vendor has no order-processing overrides"). That null-everywhere design is deliberate and it's a maintenance rule, not just a style — see §5.

2The persisted row & the .copy() idiom

The config aggregate is wrapped by the Configuration entity — the actual DB row. Note it carries the identity keys (lpvId, globalEntityId, platformVendorId) and an optimistic-lock @Version.

vendor-management-service/…/db/model/Configuration.kt@Table("configuration")
data class Configuration(
    @Id @Column val id: Long? = null,
    @Column("lpvId") val lpvId: String?,
    @Column("globalEntityId") val globalEntityId: String,
    @Column("platformVendorId") val platformVendorId: String?,
    @Column val configurations: PlatformVendorConfig = PlatformVendorConfig(),
    val createdAt: Instant = Instant.now(),
    val modifiedAt: Instant = Instant.now(),
    @Version @Column val version: Int = INITIAL_VERSION
)

Because everything is val (immutable), updates are done by producing a new object. Watch how enrichRestrictedVehiclesCountryCode "edits" a deeply-nested field:

Configuration.kt · enrichRestrictedVehiclesCountryCode (abridged)return this.copy(
    configurations = this.configurations.copy(
        orderProcessing = this.configurations.orderProcessing?.copy(
            restrictedVehicleIds = restrictedVehicles,
            restrictedVehiclesCountryCode = /* … */
        )
    )
)
Kotlin ↔ Java

Nested .copy() = immutable update. Coming from Java you'd mutate a setter. Here you rebuild the object graph: copy the outer, whose configurations is a copy of the inner, whose orderProcessing is a copy with two fields changed. Unchanged fields are carried over automatically. This is the dominant "write" pattern in the whole service.

?.copy() — the ?. is a safe call. If orderProcessing is null, the whole expression is null instead of throwing an NPE. The Java equivalent is a manual if (x != null) guard, done for you.

3Three scopes, one resolution order

The same configuration table stores configs at three different scopes, distinguished by which identity columns are set. When VMS resolves the effective config for a vendor, it layers them in priority order:

PRIORITY 1 — most specific
Platform-vendor level — lpvId + globalEntityId + platformVendorId all set. One specific restaurant listing.
▲ overrides ▲
PRIORITY 2
GEID level — only globalEntityId set (lpvId/platformVendorId null). Applies to every vendor in a global entity. Built by createPlatformConfiguration(geid).
▲ overrides ▲
PRIORITY 3 — broadest
Physical-vendor level — one kitchen (lpvId), shared by all its platform listings.

On top of these sit default configuration templates (default_configuration table), applied to vendors matching filter criteria — city, chain, or vertical — when a GEID opts in.

Maintainer's tell

You can identify a config row's scope just by reading its null columns: all three keys set → platform-vendor; only globalEntityId → GEID-level; platformVendorId null but lpvId set → physical-vendor. When debugging "why does this vendor have setting X," the answer is almost always "it's inherited from a broader scope."

The supported-vs-enabled split inside vendorAvailability is the classic example. Look at the real logic that keeps them straight:

VendorAvailabilityConfiguration.kt · computePropertyRulesprivate fun computePropertyRules(
    isSupported: Boolean?,   // ← from DWH (read-only to operator)
    property: Boolean?,      // ← operator's toggle
    platformProperty: Boolean? = null,
    other: () -> Boolean?
): Boolean? = when {
    isSupported in listOf(null, false) -> false   // not supported ⇒ force off
    property == false -> property
    platformProperty in listOf(true, false) -> platformProperty
    property == true -> property
    else -> other()
}
Kotlin ↔ Java

when { … } with no argument is a chained if/else if, but as an expression — it returns a value, which is assigned straight to the function (the = body). The first matching branch wins.

other: () -> Boolean? is a function parameter (a lambda). other() calls it. It's passed lazily so the fallback only runs if reached.

Semantics that matter for maintenance: if DWH says the platform doesn't support check-out, the operator's enabled toggle is overridden to false. Support gates enablement. You cannot enable what the platform can't do.

5Two maintenance landmines already visible here

Landmine 1 — JSONB has no schema

Because the whole aggregate is serialized into one JSONB column, the Kotlin data class is the schema — there's no DB migration when you add a field. That freedom cuts both ways:

  • Safe: add a new nullable field with a default. Old rows deserialize fine (missing → null).
  • Dangerous: renaming or removing a field silently breaks deserialization of every row written before the change. @JsonIgnoreProperties(ignoreUnknown = true) (see §1) means unknown JSON is dropped, not errored — so data loss is silent. Deprecate, never delete.
Landmine 2 — a real bug in the tree, right now

In Configuration.kt, inside the filterAndMerge extension function, there's a leftover debug line shipping in production:

println("keysToFilter:: " + keysToFilter?.joinToString { " " })

A raw println bypasses structured logging, produces no context, and (per the security rules) risks leaking data into stdout unaudited. This is exactly the kind of thing your code reviews must catch. Note it — we'll revisit logging hygiene.

Kotlin ↔ Java — one more idiom to bank

That filterAndMerge is declared as fun <K,V> Map<K,V>?.filterAndMerge(…) — an extension function on a nullable receiver. It reads like a method on Map (myMap.filterAndMerge(...)) but is defined outside the class, and can be called even when myMap is null (the body checks if (this == null)). This codebase adds behavior to types via extensions everywhere — e.g. Configuration.toConfigurationResponse(), Configuration.calculateFlags(). When you see a "method" that isn't in the class body, it's an extension function, usually at the bottom of the file or in a *Extensions.kt.
