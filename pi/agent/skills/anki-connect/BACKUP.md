# Mandatory pre-change backups

Before every deck-affecting logical operation, create and verify a fresh backup of all affected existing decks. Do this after confirmation and before the first write. This standing instruction authorizes local backup creation; it does not authorize the proposed Anki changes. Read-only inspection needs no backup.

## 1. Resolve coverage

- Include changes to decks, notes, fields, tags, cards, scheduling/reviews, models, deck configurations, and referenced media, as well as imports and sync.
- For note changes, inspect all cards generated by those notes: sibling cards may live in other decks. For moves, include both source and existing destination decks. Include affected child decks; a parent deck export can cover its descendants.
- For shared models, presets, or media, identify every affected deck, not only the one named by the user. If the scope is unknown or collection-wide (for example, sync or an unbounded import), require a full collection backup including media before proceeding.
- A new deck has no prior state to export: record that it did not exist and back up any affected existing decks. Once created, export and verify the empty deck before subsequent writes to it. Never skip backups for an existing deck just because the operation only adds data.
- A deck package is not a complete collection snapshot. For changes to state not reliably captured by deck exports, require a verified full collection backup and any additional affected media/configuration files. If that cannot be created safely through supported facilities, stop and ask the user to make it in Anki.

## 2. Choose durable storage

Use a user-specified backup directory, otherwise `~/.local/share/anki-connect/backups/` on the machine running Anki. Expand it to an absolute path; the API writes on the Anki host, not necessarily the client.

Create a private, unique timestamped operation directory (with a random suffix to prevent collisions). Name exports using deck IDs or sanitized names and the `.apkg` extension. Never use the special filename `collection.apkg`, overwrite an earlier backup, or store backups in a temporary folder, repository, or `collection.media`. Keep backups after completion; never prune them without permission.

Record the active profile, operation, original deck names/IDs, timestamp, and export paths in a small manifest beside the backups. Record nonexistent destination decks as such. Do not include API keys.

## 3. Export before writing

Check installed support for `exportPackage`. Example version-6 request (substitute the exact deck name and a new absolute path; add the configured top-level `key` if required):

```json
{
  "action": "exportPackage",
  "version": 6,
  "params": {
    "deck": "French",
    "path": "/absolute/backup-directory/unique-operation/deck-123.apkg",
    "includeSched": true
  }
}
```

- Always set `includeSched:true`; the default is false and omits scheduling data.
- At the recorded baseline, the action accepts `deck`, `path`, and `includeSched`; it delegates packaging to Anki's `AnkiPackageExporter`. Do not invent an `includeMedia` API parameter. Verify referenced media are included when needed, and separately preserve any affected files the exporter omits.
- Allow sufficient time for deck size and media. Do not omit scheduling or needed media merely to make the backup quick.
- Execute backup calls separately from modifying calls. Never put exports and writes into one `multi` batch: a failed export would not stop later actions.

## 4. Verify and gate writes

Require **both** `error:null` and `result:true`. Then, on the Anki host, verify every export exists, is nonempty, and is a readable ZIP/APKG archive with collection data (for example, inspect entries and run `zipfile.ZipFile.testzip()` with Python). Check expected media coverage where relevant. Archive integrity alone does not prove complete coverage or restorability.

If the API fails, returns false, times out, or files/coverage cannot be verified, **stop before making changes**. After a timeout, inspect the export before retrying; use a new path if another export is necessary. For a remote Anki host without filesystem access, require host-side verification rather than assuming success.

Only proceed once all required backups are verified. One backup set covers the approved logical operation's related calls; a new operation requires a fresh set. Preserve the original pre-change backups if execution partially fails. Report backup paths alongside the change results.

## Recovery limits

An `.apkg` is a recovery copy, not an automatic rollback: importing it can merge data and preserve newer notes rather than revert them, and it does not automatically remove newly added cards. Never restore/import as a verification step or retry strategy. A restore is a separate modifying operation requiring confirmation and its own pre-restore backup; inspect in a separate profile or plan a full collection restore when exact rollback is needed.
